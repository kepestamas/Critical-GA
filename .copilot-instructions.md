# GitHub Copilot Instructions for Critical-GA Project

## Project Overview
This is a research project implementing genetic algorithms and greedy algorithms for the Critical Network Disruption Problem (CNDP). The codebase focuses on network analysis, optimization algorithms, and comprehensive documentation maintenance.

## Code Quality Guidelines

### 1. Code Style and Standards
- **Follow PEP 8**: Use consistent formatting, naming conventions
- **Line length**: Maximum 88 characters (Black formatter standard)
- **Naming conventions**:
  - Variables/functions: `snake_case`
  - Classes: `PascalCase`
  - Constants: `UPPER_SNAKE_CASE`
  - Private attributes: `_leading_underscore`
- **Import organization**: Standard library → Third-party → Local imports
- **Type hints**: Add type annotations for all public functions
- **Docstrings**: Use Google-style docstrings for all functions and classes

### 2. Function Design Principles
- **Single Responsibility**: Each function should have one clear purpose
- **Pure functions**: Avoid side effects when possible
- **Error handling**: Use appropriate exception handling with descriptive messages
- **Parameter validation**: Validate inputs and provide clear error messages
- **Return consistency**: Always return the same type or use Union types

### 3. Algorithm-Specific Guidelines
- **Genetic Algorithm**: Use class-based approach, avoid global variables
- **Network operations**: Leverage NetworkX efficiently, avoid unnecessary copies
- **Performance**: Cache expensive computations, use appropriate data structures
- **Memory management**: Clean up large objects, use generators for large datasets

## Documentation Maintenance Rules

### 1. File Organization and Placement
**CRITICAL: Automatic File Placement Rules**

When creating or suggesting new files:
- **Markdown documentation files (*.md)**: ALWAYS place in `docs/` directory
  - Exception: `README.md` and `CHANGELOG.md` stay in root directory
  - All other `.md` files belong in `docs/`
  - Examples: `ALGORITHMS.md`, `API.md`, implementation plans, guides, checklists
- **Python source files (*.py)**: Place in root directory
- **Network input files**: Place in `inputs/` directory
- **Output/result files**: Place in `outputs/` directory

**Path Examples for New Documentation:**
```
✅ CORRECT:
docs/NEW_FEATURE_GUIDE.md
docs/IMPLEMENTATION_PLAN.md
docs/OPTIMIZATION_CHECKLIST.md

❌ INCORRECT:
NEW_FEATURE_GUIDE.md
IMPLEMENTATION_PLAN.md
OPTIMIZATION_CHECKLIST.md
```

**When creating new documentation:**
1. Always use full path: `docs/FILENAME.md`
2. Update README.md documentation section to link the new file
3. Ensure consistent naming: UPPERCASE_WITH_UNDERSCORES.md
4. Add to appropriate category in README documentation section

## Code Quality Checks

### 1. Before Suggesting Code Changes
Always check:
- Is the change backward compatible?
- Are all parameters properly validated?
- Is error handling appropriate?
- Will this change require documentation updates?
- Are there potential performance implications?

### 2. Performance Considerations
- Prefer NetworkX built-in functions over manual implementation
- Use `copy.deepcopy()` sparingly - consider alternatives
- Cache expensive computations (fitness evaluations)
- Use appropriate data structures (sets for membership testing)
- Consider memory usage for large networks

### 3. Testing Implications
When suggesting changes:
- Consider what tests might break
- Suggest test cases for new functionality
- Ensure edge cases are handled
- Consider both small and large network scenarios
